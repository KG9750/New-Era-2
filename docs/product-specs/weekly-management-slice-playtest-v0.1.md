## 1. 测试目的

本测试不是询问玩家“喜不喜欢这个想法”，而是观察玩家能否独立完成两周经营，并验证：

- 周初摘要能否让玩家快速识别重点；
- 每周是否只需少量有效编辑；
- 第二周是否真正继承计划；
- 供需预测和实际偏差能否被解释；
- 人物是否被记成具体的人；
- 地图瓶颈是否进入玩家决策；
- 连续时间是否产生有效决策，而不是长期最高倍速等待。

本测试不评价主题豁免、战斗、外交和十二个月战役。

## 2. 测试形式

- 形式：一对一主持测试；
- 首轮人数：5 人；
- 单场目标时长：35–50 分钟；
- 原型内容：连续两周；
- 场景：固定初始状态和固定种子；
- 记录：屏幕录像、交互日志、主持人观察和结束访谈；
- 隐私：正式候选人使用连续且不复用的 `P01`–`Pnn` 匿名编号，不在仓库保存真实姓名和联系方式。

录像和录音必须先取得测试者明确同意。不同意录像不影响参与，但主持人需要加强文字记录。

## 3. 测试者构成

首轮建议：

- 2 名熟悉殖民地模拟或复杂策略游戏的玩家；
- 2 名接触过策略游戏、但不熟悉殖民地模拟的玩家；
- 1 名较少玩复杂策略游戏、但愿意阅读基础界面的玩家。

避免：

- 参与本设计讨论的人；
- 已完整阅读 V0.4 或切片规格的人；
- 由开发者代操作的人；
- 只测试设计师和程序员。

每位测试者测试前记录：

| 字段 | 选项或说明 |
|---|---|
| 匿名编号 | P01–Pnn |
| 策略游戏经验 | 少 / 中 / 多 |
| 殖民地模拟经验 | 无 / 少 / 多 |
| 是否玩过 RimWorld | 否 / 少量 / 熟悉 |
| 是否看过本项目设计 | 必须为否 |
| 是否同意录像 | 是 / 否 |

### 3.1 候选人台账与测试顺序

正式 RC 冻结前，测试负责人必须建立至少 7 名合格候选人的受控台账。真实姓名和联系方式保存在仓库外；仓库内只保存匿名字段：

| 字段 | 说明 |
|---|---|
| 匿名编号 | 按进入合格候选人台账的顺序使用 `P01`、`P02`……，连续且不复用 |
| 玩家背景层 | 熟悉殖民地模拟 / 普通策略玩家 / 较少玩复杂策略 |
| 筛选结果 | 合格 / 不合格；不合格者不进入正式测试顺序 |
| 冻结测试顺序 | RC 前预先确定，不因预期表现或中途结果调整 |
| 场次状态 | 待测试 / 有效 / 无效 / 退出 / 仅诊断 |
| 构建编号 | 实际使用的 RC build ID |
| 无效或退出原因 | 只能使用第 3.2 节预先冻结的原因 |

执行规则：

1. 默认按冻结测试顺序邀请和测试；
2. 候选人无法出席时，在台账中保留其编号和状态，由下一名候选人递补；
3. 正式场次无效时使用下一个从未使用过的编号补足，不得把原编号重新分配给替补；
4. 不得在看到前几名玩家结果后，按经验、倾向或预期表现挑选后续样本；
5. 内部代理试玩使用 `P00` 或独立前缀，不进入正式候选人台账。

### 3.2 有效、无效与替补

正式场次只有在未触发下列任一预先冻结条件时，才可计入 Gate 的 5 名有效样本：

- 使用了错误构建、错误场景、错误规则版本或无法确认的初始状态；
- 测试中发现玩家已阅读本项目概念设计、切片规格、测试脚本或看过该 RC 的完整流程；
- 主持人违反中立原则，直接泄露关键答案、指出正确策略或代替玩家完成核心操作；
- 技术故障使玩家无法完成两周核心流程，或故障后状态与日志已不可验证；
- 玩家主动退出，未完成两周核心流程。

以下情况不得用于把场次判为无效：

- 玩家给出负面评价或拒绝继续游玩；
- 玩家采用低效、失败或设计者不认同的策略；
- 玩家未能理解摘要、预测、继承、人物或地图；
- 玩家触发 P0/P1 问题；
- 玩家需要协议允许的中性追问或最小非诱导提示；
- 玩家主动接受缺口，或没有把所有指标调绿。

可恢复的短暂技术中断不自动使测试无效；必须记录中断时长，并确认恢复后的状态和日志仍可验证。无效场次和主动退出场次仍保留原始记录，只是不进入 Gate 分母；测试负责人按台账顺序启用替补，直到取得 5 名有效样本。

## 4. 构建与场景准备

每轮测试前记录：

- 构建编号；
- Git commit SHA；
- 固定种子；
- 操作系统与分辨率；
- 输入设备；
- 测试日期；
- 已知缺陷；
- 是否使用开发者控制台；
- 是否因崩溃或阻断重新开始。

所有正式计入 Gate 的测试应使用同一规则版本。若中途修改规则：

- 新版本必须更换构建编号；
- 不得把修改前后的数据直接合并；
- 修改前的记录仍保留并标注失效原因。

`CONDITIONAL PASS` 后的正式复测必须使用新的首次玩家。原测试者可以用于诊断修订是否解决已知问题，但其复玩结果不得计入正式复测分母。复测前必须冻结新构建、复测人数、目标指标和通过阈值；复测编号继续沿用候选人台账的下一个编号，不得重新从 `P01` 开始。

## 5. 主持原则

主持人必须：

- 使用中性说明；
- 鼓励玩家说出正在考虑什么；
- 在玩家卡住时先记录时间和行为；
- 只在达到阻断阈值后提供最小提示；
- 区分玩家看懂了但不接受建议，与玩家根本没看懂；
- 记录玩家实际行为，不用结束后的自我描述替代。

主持人不得：

- 指出“正确”的三个问题；
- 暗示应该把所有指标调绿；
- 暗示应该接受或拒绝林禾的请求；
- 主动解释预测公式；
- 提醒地图路径可以优化；
- 用“你有没有注意到……”诱导肯定回答；
- 因为玩家选择不同策略就纠正；
- 在玩家失败前替其优化计划。

## 6. 开场话术

主持人只说：

> 你将管理一个四人聚落两周。
> 聚落已有能够运行的基础安排，但本周出现了一些需要决定的问题。
> 你的目标不是把所有指标都变成最好，而是让聚落按你认为合理的代价继续运行。
> 请尽量说出你正在考虑什么。我不会评价你的策略是否正确。

不要介绍具体界面结构。

## 7. 测试流程

### 环节 A：10 秒周初摘要测试

1. 打开第一周摘要；
2. 展示 10 秒；
3. 暂时遮挡或切走摘要；
4. 提问：

> 你认为这周最需要处理的事情是什么？

记录：

- 玩家主动说出的事项；
- 顺序；
- 是否说出粮食缺口、水泵维修、运输瓶颈；
- 是否混入摘要没有表达的错误问题；
- 是否能够说明至少一个“不处理会怎样”。

完成记录后恢复界面，不纠正答案。

### 环节 B：第一周规划

对玩家说：

> 请按你的判断安排第一周。完成后继续运行。

观察：

- 首次有效操作发生在哪里；
- 是否先处理摘要还是直接打开完整周计划；
- 是否试图检查全部 112 个时间块；
- 是否理解继承色块和例外色块；
- 是否主动接受某项风险；
- 是否为了调绿而反复微调；
- 是否展开预测解释；
- 是否发现地图运输瓶颈；
- 是否使用撤销；
- 是否能确认本周计划。

若玩家连续 3 分钟没有形成任何可执行判断，可以问：

> 你现在最不确定的是什么？

这不算功能提示。

### 环节 C：第一周运行

让时间正常推进，不提前告知水泵故障发生日。

观察：

- 玩家使用哪些速度；
- 何时暂停；
- 水泵故障后是否注意预测变化；
- 是否理解旧预测、新预测和变化原因；
- 是否进行周中紧急调整；
- 是否打开完整计划；
- 是否观察人物地图行为；
- 是否因人物备用行为感到困惑；
- 是否出现长时间最高倍速等待。

水泵事件后，在不打断操作的前提下标记：

- 玩家首次注意到事件的时间；
- 首次注意到供需变化的时间；
- 首次说出因果关系的时间。

### 环节 D：第一周复盘

周末复盘出现后，让玩家自行阅读，然后问：

> 哪个结果和你的预期不同？你认为为什么？

不要问“是不是水泵导致的”。

记录玩家是否能区分：

- 计划内结果；
- 已知风险兑现；
- 新事件；
- 人物或地图造成的执行偏差；
- 主动接受的缺口。

### 环节 E：第二周继承

进入第二周，不解释继承规则。

观察：

- 玩家是否意识到基础计划仍在运行；
- 是否重新检查所有人物和日期；
- 是否只处理新增例外；
- 是否理解“仅本次”“本周同类时间”“设为后续基础计划”；
- 是否把第一周一次性调整误认为永久安排。

若玩家主动询问是否必须重新排班，只回答：

> 请根据界面表达判断你认为需要处理哪些部分。

### 环节 F：人物请求

林禾提出学习请求后，观察：

- 玩家是否先看人物表达；
- 是否查看粮食影响；
- 是否寻找换人、化肥或主动接受缺口等替代方案；
- 是否把人物只理解为效率变化；
- 接受或拒绝时能否说出自己的价值取舍。

不要引导玩家接受请求。

### 环节 G：第二周结束与访谈

完成两周后依次提问：

1. 这两周你做过最重要的三个决定是什么？
2. 哪项缺口是你主动接受的？
3. 哪次预测发生了变化？为什么？
4. 你觉得哪个预测最可信？哪个最不可信？
5. 你记得哪些人物？他们有什么特点或请求？
6. 林禾的请求对你的计划产生了什么影响？
7. 地图上的位置或路线有没有改变你的安排？
8. 第二周是否需要重新排完整张表？
9. 哪一步最像管理聚落？哪一步最像填写表格？
10. 有没有哪项结果让你觉得系统没有提前告诉你？
11. 如果再玩一周，你准备保留和修改什么？
12. 你是否觉得存在一个明显固定的正确模板？为什么？

最后才可以询问：

> 你是否愿意继续玩到月末？最想看到什么后果？

这项只记录吸引力，不作为 Gate 1 的替代指标。

## 8. 指标定义

### 8.1 候选编辑与有效编辑

浏览器只统计**候选编辑组**，不自动判定 Gate 使用的有效编辑数。

一次候选编辑组是玩家一次确认提交产生的事务组，并分配稳定的动作 ID。以下分别形成一个候选编辑组：

- 一次单格活动修改；
- 一次批量选择后的统一修改；
- 一次“仅本次 / 本周同类 / 设为后续基础计划”的范围提交；
- 一次会改变路径、损耗或供需的地图调整。

同一批量事务无论影响多少格，都只产生一个候选编辑组，并另记受影响格子数。撤销和重做必须引用原动作 ID，形成可追踪的撤销链。纯浏览、展开解释和只打开完整计划不产生候选编辑组。

每周结束后，主持人依据候选动作 ID、撤销链、玩家原话和观察证据逐项裁定。一次最终有效编辑必须：

- 改变人物活动、调整范围或地图兑现方式；
- 对供需、人物状态或风险产生可见影响；
- 最终进入已确认计划，或被玩家明确撤销并能说明决策原因。

裁定规则：

1. 无意点击、拖错后立即恢复和界面误操作记为“非有效”，但保留为交互错误；
2. 一个批量事务最多计为一次有效编辑，不能按受影响格子拆分；
3. 围绕同一意图的连续撤销/重做链整体最多计为一次有效编辑；
4. 主持人不得补记日志中不存在的编辑，也不得因策略好坏改变裁定；
5. 浏览器导出的 `week1CandidateEditCount`、`week2CandidateEditCount` 只用于核对，Gate 只使用主持人逐项裁定后的每周最终有效编辑数。

Gate 汇总时：

- 第一周只使用 5 名有效样本中、经主持人裁定的第一周有效编辑数计算中位数；
- 第二周只使用 5 名有效样本中、经主持人裁定的第二周有效编辑数计算中位数；
- 第一周与第二周的中位数都必须为 3–5；
- 不得合并 10 个“玩家—周”样本；
- 不得先计算每名玩家的两周平均值再取中位数；
- 无效测试必须补足有效样本后再判定 Gate。

### 8.2 识别关键问题

玩家不用复述界面原文。能够说出以下意思即可：

- 粮食可能不够；
- 水泵需要处理；
- 运输距离造成损耗。

若玩家只说“有红色”“效率低”，但无法说明对象和后果，不计为识别成功。

### 8.3 解释预测

至少包含：

- 哪项预测发生变化；
- 一个主要原因；
- 该原因如何影响人物、设施或地图执行。

只说“系统算少了”不计为解释成功。

### 8.4 记住人物

玩家应能说出：

- 人名或清楚可识别的身份；
- 一项能力、请求、状态或行为边界；
- 该人物如何影响自己的决策。

只记住“农业效率最高的那个人”但不记得任何请求或行为，不算完整成功。

### 8.5 地图参与

以下任一行为可计为地图参与：

- 主动查看农田到粮仓路径；
- 调整临时集货点或通路；
- 因观察人物移动而修改安排；
- 在复盘中正确指出空间损耗。

仅点击系统直接高亮的按钮、不理解其作用，不计为主动参与。

### 8.6 最高倍速等待

同时满足以下条件才记为无效等待：

- 使用最高倍速；
- 没有观察地图、人物、预测或事件；
- 没有待执行的高价值选择；
- 持续时间超过该周真实时间的 40%。

如果 3 名或以上玩家出现此情况，视为有效决策密度失败信号。

### 8.7 经营周真实时长

统一计时边界：

- 第一周从周初摘要首次显示开始，到第一周周末复盘首次显示为止；
- 第二周从第二周摘要首次显示开始，到第二周周末复盘首次显示为止；
- 计时包含 10 秒摘要测试、玩家规划、暂停思考、时间运行和主持提示；
- 结束访谈不计入经营周；
- 设备、录制或程序故障造成的技术中断单独记录。

每周同时记录：

```text
净完成时长 = 原始完成时长 - 技术中断时长
```

主持提示不从时长中扣除，因为它反映了实际完成该界面所需的辅助成本；提示本身仍按 9.5 节单独记录，并用于判断测试是否有效。

### 8.8 完整检查与完整重排

这两个指标只统计第二周，从第二周摘要首次显示到第二周计划首次确认。

满足以下任一条件，记为一次**完整检查**：

- 玩家主动查看并检查至少 3/4 的人物行，且覆盖至少 5/7 的日期组；
- 玩家明确表示“第二周必须重新检查全部计划”或同义判断，即使最终没有完成全部查看。

由问题卡定位后只查看一个相关人物或少量时间块，不计为完整检查。

满足以下任一条件，记为一次**完整重排**：

- 第二周修改至少 16 个活动块；
- 第二周的日程修改同时影响至少 3 名人物，并跨至少 5 个日期。

完整重排按受影响活动块、人物和日期计算，不按候选编辑组数计算；地图调整不计入日程完整重排。单场可能同时触发完整检查和完整重排。Gate 要求至少 4/5 有效玩家在第二周两者都不发生。

## 10. 严重度

| 级别 | 定义 | 示例 |
|---|---|---|
| P0 | 核心流程无法独立完成，或测试对象失效 | 无法确认计划、预测与实际完全脱节 |
| P1 | 多名玩家误解关键因果，直接威胁 Gate | 以为第二周必须重排、认为 NPC 式隐藏计算在改产量 |
| P2 | 明显增加负担或削弱人物感，但存在绕行 | 需要多次展开才能找到请求影响 |
| P3 | 文案、布局或轻微反馈问题 | 图标难辨、次要标签不清 |

“玩家选择了设计者不喜欢的策略”本身不是缺陷。只有信息误解、无意义操作或单一最优解证据才进入问题列表。

问题计数与聚类使用以下固定单位：

- 一条**症状记录**：一名有效玩家出现的一次可复述失败表现；
- 一个**独立 P1 问题**：同一可复述症状影响至少 2 名有效玩家，且影响同一任务或关键因果；受影响玩家人数不是 P1 问题数量；
- 一个**根因聚类**：多个独立 P1 问题经日志、行为或界面检查，被归到同一界面表达或同一规则根因。

每个独立 P1 问题只能指定一个主要根因聚类，并保留其症状记录和证据。不得把同一症状按玩家人数拆成多个 P1，也不得用“都是 UI 问题”这类过宽标签把无关问题强行合并。Gate 阻塞条件是同一根因聚类包含 3 个或以上独立 P1 问题。

## 11. Gate 1 判定

### PASS

必须同时满足：

- 至少 4/5 玩家能识别三个关键问题；
- 第一周和第二周分别计算 5 名有效样本经主持人裁定的有效编辑数中位数，两周均为 3–5；
- 至少 4/5 玩家第二周既不完整检查，也不完整重排；
- 至少 4/5 玩家能解释一次预测变化；
- 至少 4/5 玩家能记住一名人物及其决策影响；
- 至少 3/5 玩家主动让地图参与决策；
- 少于 3 人出现无效最高倍速等待；
- 无未解决 P0；
- 不存在同一根因聚类包含 3 个或以上独立 P1 问题。

### CONDITIONAL PASS

核心因果成立，但存在：

- 一项指标仅差 1 名玩家；
- 可由局部信息架构、反馈或数值调整解决；
- 不要求改变周计划基本模型。

必须列出：

- 条件；
- 负责人；
- 修改版本；
- 复测人数；
- 复测通过标准。

正式复测只使用新的首次玩家，并继续使用候选人台账中的新编号。原玩家复玩只作诊断，不得替代正式复测样本。

### FAIL

出现以下任一情况：

- 多数玩家无法从周初摘要确定行动；
- 多数玩家第二周发生完整检查或完整重排；
- 多数玩家不相信或无法解释预测；
- 玩家只记得效率，不记得人物；
- 地图不进入决策；
- 固定模板明显优于其他选择；
- 修正需要引入新的大型系统；
- 两轮局部迭代后核心指标仍失败。

FAIL 后不得进入主题—豁免原型。应评估减少时间块、加强班组操作，或改用责任承诺/目标分配模型。

## 12. 汇总报告

首轮完成后生成一份 Gate 报告，至少包括：

- 构建编号和 Git SHA；
- 有效测试者构成；
- 候选人台账中的测试顺序、无效样本、替补及原因；
- 每项 Gate 的原始计数；
- 候选编辑组、主持裁定结果、完成时间和倍速分布；
- 第一周与第二周各自经主持人裁定的有效编辑数中位数，不合并为 10 个“玩家—周”样本；
- 第二周完整检查与完整重排的逐人结果；
- 原始完成时长、技术中断时长和净完成时长；
- 症状记录、独立 P1 问题及其主要根因聚类；
- 支持设计和反对设计的证据；
- 代表性玩家原话；
- `PASS / CONDITIONAL PASS / FAIL`；
- 下一轮只修改哪些内容；
- 明确不修改哪些内容。

建议保存位置：

- 匿名原始记录：`data/playtests/weekly-management-slice/<build-id>/`
- 汇总 Gate 报告：`docs/exec-plans/active/<date>-weekly-management-gate-1-report.md`

原始记录不得只保留设计者摘要。若存在录像，仓库只记录受控存储位置和匿名编号，不直接提交包含个人信息的大型媒体文件。
