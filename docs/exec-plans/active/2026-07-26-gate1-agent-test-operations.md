## 1. 目的与优先级

本合同把 Gate 1 测试拆为两条不得混淆的证据轨：

- **Gate 1A（Agent Proxy）**：用 7 个彼此独立、干净上下文的 agent 玩家，检查冻结 RC 的流程可完成性、信息因果和机械交互风险。
- **Gate 1H（Human）**：保留原玩家测试协议中的首次真人验证。当前暂缓，状态始终为 `PENDING`，直至项目 Owner 明确恢复。

本合同只补充双轨运营、上下文隔离和代理结论命名。两周切片范围、缺陷严重度、候选编辑裁定、真人样本和真人 Gate 阈值仍以现有开发计划与玩家测试协议为准。

固定边界：

1. Gate 1A 不是 Gate 1H 的替代品。
2. Gate 1A 无论得到何种结论，都不能把 Gate 1 或 Gate 2 标记为 `PASS`、`UNLOCKED` 或已获真人证明。
3. Gate 2 只在 Gate 1H 得到正式 `PASS` 后解锁。Gate 1H 为 `PENDING`、`CONDITIONAL PASS` 或 `FAIL` 时，Gate 2 均保持 `LOCKED`。
4. 里程碑代理试玩 A/B/C 是开发诊断，不计入 Gate 1A 的 7 个正式代理样本。

## 2. 测试运营负责人的职责与非职责

### 2.1 职责

测试运营负责人负责：

1. 安排并核验里程碑代理试玩 A/B/C；
2. 在 Gate 1A 开始前冻结 RC cohort manifest；
3. 创建 7 个不继承项目对话的干净 agent 上下文；
4. 向 cohort manifest 冻结的七个主样本发放内容完全相同的玩家包，不泄露评分阈值、其他样本结果或正确策略；
5. 保证每个 agent 使用全新应用会话、独立浏览器存储和相同 RC 指纹；
6. 按冻结顺序分批执行，核验只读纪律和上下文隔离；
7. 保存原始动作、导出、agent 输出、主持提示、有效性裁定、缺陷和替补链；
8. 依据冻结规则判定样本有效或无效，不因结果好坏选择样本；
9. 汇总 Gate 1A，并且只发布 `AGENT_PROXY_PASS`、`AGENT_PROXY_CONDITIONAL` 或 `AGENT_PROXY_FAIL`；
10. 始终在报告中保留 Gate 1H `PENDING` 和 Gate 2 `LOCKED`。

### 2.2 非职责

测试运营负责人不负责：

- 编写、修改或修复原型代码；
- 在测试中临时改变规则、场景、阈值或主持话术；
- 代 agent 操作、提示正确策略或筛掉负面结果；
- 把 agent 的推理速度、文字风格或模型知识解释为真人体验；
- 招募、联系或主持真人测试；Gate 1H 恢复前不启动真人运营；
- 代表项目 Owner 解锁 Gate 2；
- 虚构日期、用时、情绪、乐趣、继续游玩意愿或真人原话。

发现缺陷后，测试运营负责人只提交可复现证据和严重度建议。是否修复、如何修复由实施负责人决定；任何影响 RC 的修复都会触发本合同第 8 节的 cohort 作废规则。

## 3. 两类代理试玩

### 3.1 里程碑代理试玩 A/B/C

为避免与 Gate 1A 混淆，运营记录中使用 `M-A`、`M-B`、`M-C`：

| 标识 | 计划检查点 | 测试对象 | 必须回答的问题 | 失败后的开发纪律 |
|---|---|---|---|---|
| `M-A` | D4 | 最小纵向闭环 | 能否不经界面讲解完成“问题—编辑—预测—事件—复盘”，并从界面证据说明一次预测变化 | 停止扩展完整日程，先修复阻断根因 |
| `M-B` | D9 | 完整第一周 | 能否完成第一周，并指出一个人物、设施或空间因果 | 停止增加地图和完整第二周，先修复阻断根因 |
| `M-C` | D14 | 完整两周候选流程 | 能否完成两周、导出记录，并暴露节奏、继承、地图和复盘阻断 | 不得冻结 Gate 1A RC |

三次里程碑试玩：

- 各自使用新的 agent 上下文和新的应用会话；
- 只通过玩家界面操作，不读取实现代码、测试代码或答案型设计说明；
- 不修改仓库、代码、配置、场景、测试或构建产物；
- 可以使用当时的开发构建，因此不要求三次使用同一 SHA；
- 保留实际构建指纹、可观察行为、准确捕获的 agent 输出、阻断点和修订决定；
- 不得进入当前 cohort 的正式主样本，也不得在已经接触流程后改作 Gate 1A 替补。

`D4`、`D9`、`D14` 是相对开发检查点，不是已经发生的真实日期。现有计划中的时长是目标预算；没有工具时间戳或日志时不得补写实际用时。`M-C` 可以记录机器测得的流程耗时，但不能据此宣称真人达到“一周 6–10 分钟”。

### 3.2 Gate 1A 正式代理样本

RC4 的 A01 在暴露证据采集风险后已永久技术无效；RC4 整体作废，A02–A08
均不迁入新 cohort。RC5 的主样本固定为：

| 批次 | 样本 | 执行顺序 |
|---|---|---|
| Batch 1 | A09、A10、A11 | RC 冻结后首先执行 |
| Batch 2 | A12、A13、A14 | Batch 1 原始记录封存后执行 |
| Batch 3 | A15 | Batch 2 原始记录封存后执行 |

分批只为控制执行和证据核验，不允许在批次之间修改 RC、场景、玩家包、主持规则或结论阈值。后续批次不得收到前序批次的摘要、缺陷、策略、动作轨迹或结论。

## 5. 干净上下文、会话隔离与只读纪律

每个 A09–A15 必须满足：

1. 从空白 agent 对话启动，不继承实施、设计、里程碑试玩或其他样本的对话历史；
2. 只收到匿名编号、统一中性开场、玩家任务、可操作 RC 入口和统一结束访谈问题；
3. 不收到 Gate 阈值、期望编辑数、三个问题的标准答案、推荐策略或已知缺陷；
4. 不读取仓库源码、设计文档、测试脚本、自动化断言或其他样本记录；
5. 从全新应用状态开始，不读取任何先前 session、缓存或导出；
6. 只操作冻结 RC 的玩家界面；不得编辑文件、运行补丁、改配置、调用开发者控制台改变状态或直接注入动作；
7. 一个上下文只服务一个匿名编号。场次结束后封存，不把同一上下文用于其他编号或替补；
8. agent 之间不得通信，测试运营负责人也不得把一场的结果转述给另一场。

若运行环境允许显式控制上下文继承，应使用“不继承历史”的启动方式。全局系统规则不属于样本间泄露，但任何包含本项目答案、先前试玩或 RC 实现细节的注入都构成污染。

只读试玩的含义是：agent 玩家可以在 UI 中产生正常游戏动作并触发匿名导出，但不能修改仓库或 RC。原始记录由测试运营负责人或冻结的遥测能力保存，不能让 agent 通过编辑测试文件来补证据。

## 6. 单场执行协议

每场按同一顺序执行：

1. 核对 agent 上下文为空白；
2. 核对 cohort manifest 和浏览器全新状态；
3. 记录匿名编号和实际 RC 指纹；
4. 使用玩家测试协议中的中性开场，不讲解界面；
5. 执行摘要、第一周规划与运行、第一周复盘、第二周继承、人物请求、第二周结束；
6. 只使用协议允许的中性追问，并逐条记录；
7. 导出匿名 JSON，保存界面日志和 agent 的原始结构化输出；
8. 执行“结束并清空会话”；
9. 完成有效性裁定后封存，才开始该批次的下一场。

agent 玩家不能看到浏览器日志的评分汇总，也不能在结束后重开同一场修改答案。可恢复的工具中断必须保留中断前后证据；不可恢复时按无效样本处理。

## 8. 有效、无效、替补与 cohort 作废

### 8.1 有效样本

样本只有同时满足以下条件才有效：

- 使用冻结 cohort 的全部指纹；
- 上下文和应用会话均为全新且相互隔离；
- 未接触本项目答案型材料或其他样本结果；
- 主持未泄露策略或代操作；
- agent 遵守只读纪律；
- 完成两周核心流程，或因原型自身可复现的阻断而无法完成；
- 动作、关键事件和导出证据可验证。

“因原型自身可复现的阻断而无法完成”是有效的负面结果，通常形成 P0；不得为了补齐完成率而把它判为无效。

### 8.2 仅允许的无效原因

- 错误或无法确认的 RC、场景、初始状态或协议；
- 上下文继承、样本间泄露或提前接触答案型材料；
- 主持泄露关键答案、推荐策略或代操作；
- agent 读取源码、测试或设计答案，或违反只读纪律；
- 不可恢复的运行工具故障导致核心证据不可验证；
- agent 服务中断、主动退出或输出丢失，且无法完成核心流程。

以下均不得作为无效理由：

- 负面评价、差策略或理解失败；
- 编辑次数超出预期；
- 未理解预测、继承、人物或地图；
- 触发 P0/P1；
- 没有形成设计者偏好的计划；
- agent 输出不支持预期结论。

### 8.3 替补

- A09–A15 是 RC5 冻结的主样本编号；
- 无效样本保留完整原始记录，编号永不复用；
- 替补按 `A16`、`A17`……连续递增，并使用同一 cohort 指纹和全新上下文；
- 不得根据前序结果挑选模型、提示方式或替补顺序；
- Gate 1A 只在取得 7 个有效样本后计算结论。

七样本尚未齐备时只能报告运营状态 `PENDING` 或 `RUNNING`，不能提前发布 Gate 1A 结论。

### 8.4 规则或 RC 变更后的作废

当前 cohort 的首个主样本开始后，发生以下任一变化，当前 cohort 不得再用于新的 Gate 1A 汇总结论：

- Git SHA、构建内容、场景、固定种子或初始状态变化；
- 影响决策的 UI、文案、数值或规则变化；
- 玩家包、主持脚本、有效性规则或结论阈值变化；
- 为某一批次定制提示、答案或运行条件。

变化前的记录永久保留并标记 `superseded`，不能与变化后的样本合并。修复后必须生成新的 cohort manifest，并用 7 个新的干净 agent 样本从头执行。只修正不影响语义的记录笔误或补充已有文件校验和，不构成规则变化，但必须留下审计说明。

批次之间发现普通负面结果时继续执行冻结 cohort，不得边测边修。若发现使后续场次无法进入核心流程的全局 P0，可停止该 cohort 并发布 `AGENT_PROXY_FAIL`；修复后仍须重开完整七样本 cohort。

## 9. Gate 1A 结论合同

Gate 1A 只评估可由 agent 代理观察的流程和因果，不复刻真人 UX。以下阈值仅使用同一 cohort 的 7 个有效样本。

### 9.1 `AGENT_PROXY_PASS`

必须同时满足：

- 7 个有效样本均完成可验证记录，且没有 cohort 指纹或隔离违规；
- 至少 6/7 同时能从摘要复述三个关键问题、完成两周核心流程并导出结果；
- 第一周和第二周分别计算主持裁定有效编辑数中位数，两周均为 3–5，不合并 14 个“agent—周”样本；
- 至少 6/7 在第二周既不完整检查，也不完整重排；
- 至少 6/7 能依据界面证据解释一次预测变化；
- 至少 6/7 能复述一名人物及其对决策的影响；
- 至少 5/7 通过可观察动作让地图进入决策；
- 无未解决 P0；
- 不存在同一根因聚类包含 3 个或以上独立 P1 问题。

该结论只表示“冻结 RC 通过代理流程与因果预检，可以在真人轨恢复后作为 Gate 1H 候选 RC”。它不表示真人可用性、乐趣、节奏、信任、记忆或吸引力已经通过。

### 9.2 `AGENT_PROXY_CONDITIONAL`

仅当以下条件全部满足时使用：

- 核心计划—预测—事件—复盘因果成立；
- 只有一项上述计数指标仅差 1 个 agent；
- 无未解决 P0；
- 问题可由局部信息架构、反馈或数值调整解决；
- 不要求改变周计划基本模型或引入新大型系统。

结论必须写明条件、责任人、拟修改版本和重测标准。若实际修改 RC 或规则，旧 cohort 按第 8.4 节作废，必须以新的 7 个干净样本重新形成结论，不能用局部补测把旧结果升级为 `AGENT_PROXY_PASS`。

### 9.3 `AGENT_PROXY_FAIL`

出现以下任一情况即为 `AGENT_PROXY_FAIL`：

- 任一代理阈值差距超过 conditional 范围，或两项及以上阈值失败；
- 存在未解决 P0；
- 同一根因聚类包含 3 个或以上独立 P1；
- 多数 agent 无法完成核心流程、理解继承或解释预测；
- 修正需要改变周计划基本模型或引入新的大型系统；
- cohort 因全局阻断无法继续取得有效样本。

失败后不得把该 RC 交给 Gate 1H，也不得开始 Gate 2。实施负责人先处理根因，随后冻结新 RC 和新 cohort。

### 9.4 不进入 Gate 1A 结论的真人指标

以下内容只能由 Gate 1H 验证，不得用 Gate 1A 填充：

- 真人一周是否达到 6–10 分钟；
- 真人的阅读、反应、学习和决策速度；
- 真人情绪、乐趣、挫败、沉浸和信任；
- 真人是否愿意继续到月末；
- 代表性真人原话；
- agent 的鼠标路径或工具延迟能否代表普通玩家；
- 真人总体 UX 是否 `PASS`。

Gate 1A 可以保留机器耗时、速度档位和等待轨迹作为诊断数据，但不能据此替代玩家测试协议中的真人时间和有效决策密度结论。

技术场统一使用 `TECH-*` 运营标识并排除 Gate 1A、Gate 1H 分母。RC5 捕获验证
已使用 payload 内匿名编号 `P98`；该既有 raw 证据不得改写，但 `P98` 从此永久
保留为技术编号，Gate 1H 恢复后不得分配给真人。其他技术场不得再占用 `Pxx`
真人命名空间。

## 10. Gate 1H 与 Gate 2 锁
