# 《新纪元 2》分阶段游戏开发与 Godot AI 工作流

## 1. 目的

本工作流把产品假设、代码实现、编辑器操作、独立审查、冻结试玩和 Gate
决策接成一条可验证的交付链。它解决的是“谁在什么阶段、依据什么事实、用什么
证据完成工作”，不替代具体玩法规格或活跃执行计划。

固定主链：

```text
玩法假设
  → 最小实现
  → 自动验证
  → 编辑器或运行态验证
  → 独立复核
  → 冻结试玩
  → Gate 决策
```

## 2. 权威来源与冲突顺序

开始任务前按顺序读取：

1. [`AGENTS.md`](../../AGENTS.md)
2. [`CONTEXT.md`](../../CONTEXT.md)
3. [`PLANS.md`](../../PLANS.md)
4. 当前 Gate 的产品规格和活跃执行计划
5. [`FRONTEND.md`](../../FRONTEND.md) 或经批准的 Godot 实施约定
6. 当前冻结 RC、cohort manifest 和对应证据

冲突时按以下优先级处理：

1. Gate 纪律、玩家测试协议和 Owner 的明确授权；
2. 当前产品规格；
3. 当前活跃执行计划；
4. 本工作流；
5. 完整游戏愿景和未来阶段设想。

`CONTEXT.md` 只是本地入口。正式 Gate 工作还必须核对目标远端 ref、RC
提交和证据目录；不得因为本地 checkout 能打开就把它当作当前真相。

## 3. 当前介质边界

### 3.1 Gate 1–2

- React + TypeScript + Vite Web 是权威原型介质。
- 无 React、DOM、存储和真实时钟依赖的 TypeScript 模拟内核是规则权威。
- React 负责呈现和玩家输入，不复制模拟规则。
- Godot AI 只属于隔离的工具链验证或经明确授权的技术 spike。
- [`spikes/godot-ai-smoke`](../../spikes/godot-ai-smoke/README.md) 不得成为
  Gate 1 或 Gate 2 的权威实现。

### 3.2 Gate 3 候选

只有 Gate 2 通过并形成新的实施计划后，才考虑用 Godot 制作单次自由意志日
战术垂直切片。首个 Godot 正式切片仍保持最小范围：

- 一张简化进攻地图；
- 固定出击队和留守队；
- 战前装备、撤退线、防区和医疗预案；
- 主战场直接控制与家园态势面板；
- 可复现、可重放的后台结算。

不得因为 Godot AI 已安装，就提前迁入 NPC 聚落、三个月成长、完整战斗、
正式美术或复杂外交。

### 3.3 规则迁移

从 TypeScript 迁入 Godot 时只允许一个规则权威：

1. 冻结输入夹具、种子、动作序列和期望结果；
2. 在旧内核生成 golden fixtures 和结果哈希；
3. 在 Godot 候选内核逐项复现；
4. parity tests 全部通过后再切换权威；
5. 切换完成后删除或明确封存旧运行路径。

禁止让 TypeScript 与 GDScript/C# 同时独立演化同一套结算规则。

## 4. 角色与权限

| 角色 | 负责 | 不负责 |
|---|---|---|
| 项目 Owner | 决定 Gate、范围、产品取舍和是否接受阈值变化 | 代替证据链证明实现通过 |
| 主实施 Agent | 代码、数据、测试、构建、文档和证据准备 | 独立裁定自己的正式试玩结果 |
| Godot AI | 场景、节点、资源、UI、运行、截图、日志和性能操作 | 决定产品范围或成为规则权威 |
| 独立审查 Agent | 只读检查缺陷、范围漂移和证据完整性 | 在审查中顺手修改候选 |
| 代理试玩 Agent | 在干净上下文中操作冻结玩家界面 | 读取源码、测试、阈值或其他样本 |
| 真人玩家 | 验证理解、节奏、乐趣和主观体验 | 被代理样本或自动化替代 |

主实施者、独立审查者和正式试玩者必须保留职责隔离。人手不足时可以顺序执行，
但不能把同一上下文的自测改名为“独立证据”。

## 5. 单任务执行合同

每项实现开始前填写以下最小合同：

```md
## 任务合同

- Issue / Task：
- 目标 Gate：
- 要验证的玩法或技术假设：
- 允许修改：
- 明确不做：
- 权威输入：
- 玩家可观察结果：
- 自动验收：
- 运行态验收：
- 所需证据：
- 会使既有 RC/cohort 失效的变更：
```

如果不能写出“玩家可观察结果”和“所需证据”，任务仍处于探索阶段，不得进入
正式 RC。

## 6. 三层执行循环

### 6.1 任务循环

适用于一个缺陷或小功能：

1. 读取权威输入并记录假设；
2. 先建立可复现测试或失败证据；
3. 做满足任务合同的最小改动；
4. 运行相关单元、组件或规则测试；
5. 在真实呈现介质中操作玩家路径；
6. 保存结果并检查作用域；
7. 只关闭当前任务产生的缺陷和遗留。

### 6.2 功能循环

适用于一条玩家因果闭环：

```text
问题或事件
  → 玩家选择
  → 计划或状态改变
  → 预测立即变化
  → 时间运行
  → 后果发生
  → 复盘解释偏差
```

功能完成必须同时证明：

- 玩家能够执行选择；
- 状态变化来自权威内核；
- 界面能说明主要原因；
- 相同输入得到相同结果；
- 事件、日志和复盘没有互相矛盾；
- 自动化与真实交互至少各覆盖一次主路径。

### 6.3 Gate 循环

适用于正式候选：

1. 形成不可变 RC；
2. 固定 Git SHA、构建哈希、场景、种子、初态、协议、玩家包和视口；
3. 完成独立冻结复核；
4. 使用全新上下文、全新应用会话和相同 RC 执行样本；
5. 原始记录、下载、校验和、访谈和有效性裁定逐场封存；
6. 依据预先冻结的阈值汇总；
7. 发布精确的 `PASS`、`CONDITIONAL` 或 `FAIL`，不得用“流程完成”替代指标；
8. 任何影响玩家决策或统计口径的修复都生成新 RC 和新 cohort。

单次技术试玩、里程碑试玩或 RC9 类盲测成功，只证明对应受限流程完成；除非
完整 Gate 合同也得到满足，否则不得据此宣称 Gate 已通过。

## 7. Web 主线的验证闭环

Gate 1–2 的每项改动至少执行：

1. TypeScript 严格检查；
2. 相关 Vitest 规则与组件测试；
3. 生产构建；
4. Chromium 主流程 E2E；
5. 冻结视口下的真实 UI 操作；
6. 匿名导出、下载、校验和与清空验证；
7. 确定性种子、初态和结果哈希检查；
8. 证据目录和 RC manifest 检查。

盲测若规定 `INITIAL_OBSERVATION`、`CONTINUE_PLAY`、`CLEAR_AUTHORIZED` 等
门控，必须把它们当作证据合同，而不是可跳过的操作提示。

## 8. Godot AI 编辑器闭环

### 8.1 进入条件

只有满足以下任一条件才使用 Godot AI：

- 在隔离 smoke 项目验证工具链；
- 当前任务明确属于已批准的 Godot spike；
- Gate 已解锁 Godot 垂直切片，且活跃计划明确指定 Godot。

### 8.2 固定操作顺序

```text
列出并激活 editor session
  → 读取 editor state
  → 读取场景树、选择和相关资源
  → 执行最小场景或属性修改
  → 保存场景
  → 运行项目
  → 通过真实输入验证路径
  → 截图
  → 读取 game/editor logs
  → 必要时读取 performance monitors
  → 停止项目
  → 记录证据
```

要求：

- 必须先连接到明确的 editor session；不得依赖“当前活动窗口”猜测目标项目。
- 写操作前确认编辑器 `readiness=ready`。
- 节点、资源和场景路径必须来自现场读取，不凭记忆构造。
- 修改后必须保存场景，再做运行态验证。
- 驱动游戏后必须读取游戏日志和编辑器日志，不能只凭截图宣布通过。
- 性能任务至少记录目标场景、分辨率、FPS、内存、绘制调用和节点数。
- smoke 项目只验证桥接能力；不得把 smoke 截图当作游戏功能证据。
- Godot headless 模式不能替代需要真实 EditorPlugin 会话的 MCP 验证。

### 8.3 Godot 功能完成定义

一个 Godot 功能只有同时满足以下条件才完成：

- 场景树和资源引用正确；
- 场景已保存且重新打开后仍成立；
- 游戏可启动、可交互并能到达预期状态；
- 游戏日志和编辑器日志无未处置错误；
- 目标视口截图通过视觉检查；
- 相关性能预算通过或明确记录偏差；
- 纯规则测试或 parity tests 通过；
- 证据绑定准确的 Git SHA、Godot 版本和场景路径。

## 9. 独立审查

独立审查采用只读方式，至少检查：

- Gate 和范围是否被静默扩大；
- 产品规格、模拟内核和 UI 是否表达同一规则；
- 错误处理是否掩盖无效状态；
- 测试是否只验证实现细节而漏掉玩家结果；
- 证据是否绑定正确版本；
- “自动化通过”“代理通过”“真人通过”是否被混淆；
- 是否存在 P0、冻结前必须解决的 P1 或系统性 P2。

审查报告必须包含严重度、精确位置、复现或推理证据、最小修正和明确结论。
报告通过不等于 Gate 通过。

## 10. 工作树与版本纪律

正式 RC、独立审查和 Gate 测试不得直接使用来源不明的脏工作树。

开始前至少检查：

```bash
GIT_CONFIG_GLOBAL=/dev/null git status --short --branch
GIT_CONFIG_GLOBAL=/dev/null git ls-remote origin <target-ref>
GIT_CONFIG_GLOBAL=/dev/null git show <verified-ref>:CONTEXT.md
```

若当前工作树落后远端或混有其他任务：

1. 保留原工作树，不清理、不 reset、不覆盖；
2. 从现场核验的 ref 创建独立 clean worktree；
3. 在 clean worktree 中构建和冻结；
4. 只提交与任务合同直接相关的文件；
5. 不使用 `git add -A` 收集混杂改动。

远端暂时不可达时，可以继续编写不依赖当前 Gate 状态的通用文档，但不得冻结
RC、启动正式样本或发布新的 Gate 结论。

- [ ] 确定性结果通过

### Godot 功能

- [ ] 目标 session、版本和场景已记录

- [ ] 运行和真实输入通过

### RC / Gate

- [ ] clean worktree 和不可变 ref
- [ ] manifest 与 artifact hash
- [ ] 独立冻结复核

- [ ] 结论严格使用冻结阈值
- [ ] 未把代理或自动化证据写成真人结论
